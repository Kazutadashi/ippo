# Project notes for Claude

## Coding principles (binding)

Follow `CONTRIBUTING.md` for all code in this repo, every session, without
being reminded. In short: beginner-readable, simple over clever, Zen of
Python in spirit, thorough doc comments, comments that explain why, small
files and functions, minimal dependencies, no code generation, no network
access. When unsure between two approaches, pick the more obvious one.

Auditability is a first-class goal: users should be able to trust the
app by reading its code. All file access goes through one small storage
part of the core; no `INTERNET` permission in release builds; every
permission and dependency is documented with a reason
(`docs/permissions.md`, `docs/dependencies.md`). See the Auditability
section of `CONTRIBUTING.md`.

## What this project is

**Ippo** (一歩, "one step", from 千里の道も一歩から: "a journey of a
thousand miles begins with a single step"). A personal health app meant
to become a generic, open-source app that
other people can use and extend. It is a Loop-Habit-Tracker-style app
plus more, built from modules:

1. Habits: daily check-offs, history, Loop-style habit strength score.
2. Calisthenics progression: exercise ladders (Hybrid Calisthenics
   style), log sets/reps, prompt to move up a step at a rep target.
3. Meal diary / calorie tracker.
4. Time tracker: tap to start an activity; starting the next one ends
   the last. Shows how each day was spent (for example a pie chart).
5. Sleep: bedtime and wake-up for each night, plus naps.

The main purpose of every module is longitudinal tracking: data must
be easy to chart and to use for time series and machine learning.
Record raw observations (not judgements like "good"), stable IDs,
the day an entry is about, and explicit units.

**The data is the product.** Future data scientists, statisticians and
researchers using this data are the most important audience, above the
in-app display. Every decision is weighed first by what it does to the
data: standard vocabularies and units, compatibility with analysis
tools, easy access and extraction, and nothing ambiguous or missing
without saying so. The binding rules are in `docs/data-principles.md`.
Breaking the format is acceptable when it makes the data clearly
better, with a converter for existing data; losing or silently changing
data is not.

More modules should be addable without touching existing ones.

Toolchain setup for contributors: `docs/development-setup.md`.

License: GPL-3.0-or-later (`LICENSE`). Every source file starts with an
`SPDX-License-Identifier: GPL-3.0-or-later` comment. Intended for F-Droid.

## Architecture decisions

- **Flutter**, one codebase for Android and Linux desktop.
- **No server, no network.** The app reads and writes plain files in a
  data folder the user picks in settings. It must work with any folder;
  never hard-code paths. Syncing between devices is the user's job
  (for example Syncthing, or a NAS's own sync app).
- **Append-only event log, one file per device**:
  `<data folder>/events/<device id>.jsonl`. The device id is random,
  generated once per install (names can collide; ids cannot). A device
  only ever writes its own file and reads all of them. This avoids sync
  conflicts. Each file is one continuous log for all time (no monthly
  splitting), so users can copy it over USB and load it directly.
- Monthly snapshots of the device's own file go to
  `<data folder>/backups/`. The app never reads them; they are only a
  safety net.
- Merging is a union of all events, deduplicated by event id. Readers
  also pick up sync-tool conflict copies, ignore hidden files, skip
  unparsable lines (warning the user, never changing the file), and
  skip unknown event types and fields so older app versions keep working.
- **Android storage**: a small hand-written Kotlin bridge over the
  Storage Access Framework (no third-party plugin, no storage
  permission). The user picks a folder; the app can only touch that one.
  Linux uses `dart:io`. Both sit behind one storage interface in the core.
- Event ids are UUIDv7 (RFC 9562), generated by hand.
- Each line is one JSON event with: a format version, a unique id, an
  ISO 8601 timestamp with time zone offset, the device id and name, the module,
  the event type, and module-specific data. Edits and deletions are new
  events referencing the original id. Full spec to be written in
  `docs/data-format.md`.
- App state is rebuilt by reading and merging all event files by
  timestamp. Conflicting changes: the most recent timestamp wins (ties
  broken by event id). No logical clocks; warn about future-dated events.
- Data must stay easy to analyze in Python (pandas, Jupyter, ML).
  The Python package in `python/` (pandas only) turns a data folder into
  tidy tables and CSV files. `example-data/` is a small folder with every
  awkward case; the Dart and Python tests check the same answers from it,
  so a format change must update both.
- Show when data from each other device was last seen, so users can tell
  if sync has caught up.

## No personal information in the repo

Nothing committed here may reveal anything about the owner or any other
real person: no names, emails, usernames, file paths, home directories,
environment variables, device names, habits, foods, workouts, schedules,
or details of their hardware, OS, or sync setup. Paths are always chosen
by the user at runtime or built from platform APIs, never written out.
(Git commit author info is fine and not covered by this rule. The one
other exception is the app id, `io.github.kazutadashi.ippo` in
`android/app/build.gradle.kts` and `linux/CMakeLists.txt`: based on the
project's public GitHub address, by the owner's choice, because an app
id can never change once released. Use it nowhere else.)
Examples, defaults, tests, and sample data use generic placeholders (`my-phone`, `/path/to/data`, "Read 10 pages"). The owner's
own configuration lives only in their data folder, never in the code.
